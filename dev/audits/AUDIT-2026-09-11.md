# Vanilla Questing — external audit, 2026-09-11

Reviewed at 61 commits / v1.0.0. Test suite run locally: 728 checks, 0 failures.

The build is sound. These are ordered by severity, and the first one is the only
one I'd block a release on.

---

## 1. BLOCKER — tracker item buttons are hidden without a protection check

**Where:** `Tracker.lua`, `hideTrackerItemButtons` → `trackerPass`, `pcall(b.Hide, b)`
on `WatchFrameItem1..N`.

**The claim being relied on:** SPEC.md ~line 1546 — "`WatchFrame:IsProtected()` →
`false`, explicitly false. Safety rule 1 is satisfied: it can be touched, in combat
included." Restated in the Tracker.lua header comment.

**The problem:** that measurement was taken on `WatchFrame`, the parent. The item
buttons are a different object, and they are the quest-item *use* buttons — the one
part of the tracker most likely to be secure, because using an item is a protected
action. `grep -r WatchFrameItem dev/` returns nothing: no probe ever tested them.

**Why it's hard to catch:** `trackerPass` runs from a `hooksecurefunc` on
`WatchFrame_Update`, which fires in combat when objectives tick. Every call is
`pcall`'d, so a blocked `Hide()` is swallowed. The player sees a bare "Interface
action failed because of an AddOn" with nothing pointing back here.

**Do:**
- [ ] Extend the recon probe: `WatchFrameItem1:IsProtected()`, `:GetObjectType()`,
      `:GetAttribute("type")`. Run it and record the result in SPEC.md.
- [ ] Regardless of the result, switch from `Hide()` to `SetAlpha(0)` +
      `EnableMouse(false)`. Alpha is not protected, so the combat question stops
      existing. Store and restore the previous alpha the way `trackerPlainText`
      already stores mouse state.
- [ ] If you keep `Hide()`: gate `trackerPass` on `InCombatLockdown()` and re-run
      it on `PLAYER_REGEN_ENABLED`. No module currently registers that event.
- [ ] Correct the SPEC.md line so it says what was actually measured. A future
      reader will lean on it again.
- [ ] `hiddenOnes` is written and never read. Remove it or use it.

## 2. Taint — `ShowUIPanel` / `HideUIPanel` called from addon code at login

**Where:** `CVars.lua` → `doCycleWorldMap`.

Calling Blizzard's UI panel manager from addon code taints it. The reachable path is
`PLAYER_ENTERING_WORLD` → `ApplyAll` → `Enable` → `writeCVar` → `refreshQuestUI` →
`cycleWorldMap`, i.e. any loading screen where `questPOI` has drifted. The
`InCombatLockdown` guard prevents the immediate error, not the taint — which shows
up later as an unrelated blocked action.

**Do:**
- [ ] Only cycle the map from a user-initiated change (`ns:Set`, the options panel).
      Never from the event-driven re-assert path.
- [ ] Note the taint risk next to the existing comment, which currently only
      discusses the combat error.

## 3. A refused CVar write is permanent and blocks the restore

**Where:** `CVars.lua` — `refused[rule.cvar]`, and the early return in `M:Disable()`.

`refused` is set on any failure and never cleared, so (a) one transient failure kills
that option for the session, and (b) `Disable` won't restore the player's original
value, because it returns early on the same flag. The addon keeps a change it has
made itself impossible to undo. This contradicts the README's "every value it changes
is remembered first and put back."

**Do:**
- [ ] Let `Disable` restore regardless of `refused`. A write that failed on the way
      in may well succeed on the way out, and a failed restore costs nothing.
- [ ] Clear `refused` on `PLAYER_ENTERING_WORLD` so a transient failure gets one
      retry per session rather than none.

## 4. The Blizzard-options mirror has no settled gate

**Where:** `CVars.lua` → the `CVAR_UPDATE` handler.

The handler loops over every rule on *any* CVar change. During login the client fires
`CVAR_UPDATE` for unrelated variables. If one arrives before `ApplyAll` has written
`autoQuestWatch`, the mirror reads the pre-addon value, concludes the player changed
it in Blizzard's options, flips the saved setting off and prints a line saying so.

`Minimap.lua` guards precisely this case with its `settled` flag. `CVars.lua` doesn't.

Related: the `applying` re-entry guard assumes `SetCVar` fires `CVAR_UPDATE`
synchronously. WoW queues events, so `applying` is back to false by the time the
handler runs. Benign today only because the values agree by then — and this is the
one case where they don't.

**Do:**
- [ ] Add a `settled` gate matching Minimap.lua: ignore mirror updates until one
      full `ApplyAll` has completed after `PLAYER_ENTERING_WORLD`.
- [ ] Fix or delete the `applying` comment so it describes real behaviour.
- [ ] Add a test scenario: `CVAR_UPDATE` arriving before the first `ApplyAll` must
      not change any saved setting.

## 5. Tooltip `Disable()` leaves the frame pinned

**Where:** `Tooltip.lua` — `__vqPinned`, set in `fitHeight`, never cleared.

`Disable()` says there is nothing to restore, but `scrub` and `onSizeChanged` both
bail on the settings check, so nothing returns the frame to self-sizing. By the
module's own comment — "setting a height PINS the frame ... this AddOn owns the
height and has to keep setting it" — turning the option off strands GameTooltip at
whatever the last scrubbed tooltip needed.

**Do:**
- [ ] Clear `__vqPinned` and `__vqBlankedAt` in `Disable()`.
- [ ] Work out in game what actually restores auto-sizing (`SetHeight(0)`, or a
      `ClearLines` + rebuild) and do that. Verify by hovering a long tooltip, a
      short one, then toggling off and hovering both again.

## 6. Minor — `Bags.lua:Disable` calls `ContainerFrame_Update` directly

Hooking it is correct. *Calling* it runs Blizzard's container code on a tainted path,
and bag buttons are taint-sensitive. `QuestFrame.lua` already takes the better line:
"which quests have a portrait is the game's business." Do the same here — let the
next natural redraw restore the highlights.

## What's working, and worth not regressing

- Recon-before-code. It caught that `Minimap:SetQuestBlob*` doesn't exist here and
  that the map is a modern canvas — both of which would have been wrong guesses.
- `MINIMAP_TRACKING_QUEST_POIS` resolved by name, never by index. The comment
  explaining why (indices shift with class and profession) is exactly right.
- 12 failure scenarios in the harness, plus a forward-reference linter that catches
  a class of bug `luac -p` accepts.
- Release workflow failing loudly on a toc/tag mismatch.
- Limitations documented rather than quietly worked around.
