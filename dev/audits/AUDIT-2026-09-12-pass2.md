## 2. New doc inconsistencies introduced by the doc pass

### 2a. AGENT.md asserts a public promise that is no longer public

AGENT.md: "That promise is made in public, in the readme and on CurseForge. **Any
path that keeps a change is a bug against the AddOn's central claim.**"

The README dropped the no-trace claim in this same pass. The CurseForge page never
carried it. So the justification for treating findings 3 and 5 as central bugs now
rests on a public commitment that exists in neither public place.

- [ ] Either put the promise back somewhere public and keep the severity, or reword
      AGENT.md to say the promise is an internal design rule. Don't leave it claiming
      a readership it doesn't have.

### 2b. The CurseForge row was removed from the doc-sync table

Known limitations used to be a three-way must-agree: README, SPEC, listing. AGENT.md
now makes it two-way and demotes the listing to "flag it in the reply." But the
listing still has a Known limitations section — so there are still three copies, and
the one that can't be checked from the repo is the one no longer governed by the rule.

- [ ] Put a CurseForge row back in the table. "Cannot be automated" is the argument
      for a stronger rule, not a weaker one.

## 3. New code findings

### 3a. `applyingPreset` is declared twice — Options.lua:811 and Options.lua:839

Nothing between the two lines reads or writes it; line 839 shadows line 811 for
everything after. `ns.SetPresetApplying` (887), `onSettingChanged` (862) and the
Apply-button hook (1261) all bind to the second. The first is dead.

Harmless as it stands. It becomes a silent bug the first time someone adds a
reference between 811 and 839. `lint_forward_refs.py` does not catch duplicate
locals.

- [ ] Delete the declaration at 811.
- [ ] Consider extending the linter to flag a `local` name redeclared at the same
      scope in one file.

### 3b. Contradictory comments on `noAutoQuestTracking` — CVars.lua:34–45

Four lines apart, on the same rule:

> "This is real quality of life, not clutter, so it ships off and the player chooses
> it rather than having it chosen for them."

> "Ships ON: the Full Classic experience is what people install this AddOn for, so a
> fresh install gives exactly that."

`default = true`. The first comment is a survivor of a reversed decision. In a file
where the comments are relied on as the record of *why*, a stale one is worse than
none.

- [ ] Delete the first comment. Check the other rules for the same residue.

### 3c. Worth a look, not yet a finding

`doRebuild` calls `ReloadUI()` from the settings-changed callback with no combat
guard. The Settings panel can be open in combat. Confirm whether `ReloadUI` is
callable there on this client, and whether reloading mid-fight is behaviour you want
even if it is permitted.

## 4. CurseForge listing

### Working — don't change

Summary describes the project, not the author. Ko-fi at the bottom, civil in size,
nothing paywalled — compliant with CurseForge's own rules. Licence declared. Correct
flavor (MoP Classic) and game version (5.5.4). Known limitations section present and
matching the README. The two before/after screenshots carry the pitch better than the
prose does.

### 4a. The page never mentions that any of this is configurable

No reference to the options panel, to `/vq`, or to per-option switching anywhere on
the listing.

The reader's fear is "this will rip twelve things out of my UI at once." The page is
a twelve-item list of removals with nothing addressing that. The README's own tagline
— *"You have full control, disable as much or as little as you like"* — is the single
strongest line you have and it isn't on the page.

- [ ] Add a short section above **What it changes**: options panel, `/vq`, everything
      individually switchable, and the presets.
- [ ] Mark which options ship on by default, and which are experimental and off.

### 4b. No uninstall note

Delete the folder and `questPOI`, `showBosses` and `autoQuestWatch` stay where the
AddOn left them, with nothing in the game to explain it. This is a support ticket
waiting to happen, on a page whose only support route is a GitHub issue.

- [ ] One line: run `/vq off` before uninstalling. Add it to the README too — it's
      still missing there.

### 4c. Banner is hotlinked from raw.githubusercontent.com

```
https://raw.githubusercontent.com/wickoc/vanilla-questing/refs/heads/main/.github/vanilla-questing-banner.png
```

The other two images are on `media.forgecdn.net`. GitHub raw is not an image CDN, is
rate-limited, and will 404 on a public listing if the file moves or the repo goes
private.

- [ ] Upload the banner to CurseForge and point the listing at the forgecdn URL.

### 4d. Two errors in the opening paragraph

- "a numbered markers on the map" — leftover from an edit.
- "you work out where it means" — garbled; intent is "what it means" or "where it
  means you to go."

First paragraph, above the fold. Proofread the rest of the page in the same pass.

### 4e. Verify the support route actually works

The listing says **"Open an issue on GitHub"** and "bug reports and feature requests
are genuinely welcome." The repo's issues page renders **"Issue creation is
restricted in this repository."**

I was signed out, so this may be the signed-out message rather than the setting. But
if the restriction is real, the listing's only support channel is closed and the page
offers no fallback contact.

- [ ] Check Settings → Issues while signed in.
- [ ] Either open issue creation, or put a second contact route on the listing.

### 4f. Licence contradicts the invitation to contribute

"All rights reserved" alongside a public repo, a `good first issue` label, and
"feature requests are genuinely welcome." Under that licence nobody may legally fork
or submit a patch.

- [ ] Decide. If contributions are wanted, add a permissive LICENSE file (there is no
      LICENSE in the repo at all) and change the CurseForge licence field. If not,
      drop the `good first issue` label and reword the invitation to bug reports only.
